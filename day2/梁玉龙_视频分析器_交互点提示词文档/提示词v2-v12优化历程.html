整体变化 逐版设计 优化认识

01 / ARC先看整体变化

阶段版本主要设计问题关键变化
事实基线 v2 模型是否先把视频内容说对 只输出事实事件，不输出交互点；澄清音频可用性与采样局限
严格动作前打点 v3–v5 如何避免把普通镜头、已完成动作硬判为机会 从最多两点逐步收紧为一点；要求准备线索、后续动作和时间顺序
有声整段视频 v6–v7 直接视频与音频如何参与判断 不再要求采样帧时间戳；加候选声画来源；v7 用三段状态证据进一步收紧
通用化与边界扩展 v8–v9 如何摆脱单一素材，允许“只拍到准备”的机会 v8 详细事件→单个候选；v9 加跨题材 few-shot 和 action_observed=false
连续动作中的交接 v10 没有静止准备姿态时能否打点 最初强调接应/取得控制；当前文本改为通用事件、可见决策与关键物体
开放式机会发现 v12 严格证据/后续动作约束是否过早过滤候选 不限点数，只要求定位、机会、理由；用跨题材示例展示多个点

02 / VERSIONS逐版设计与相对变化

v2：事实理解基线

为什么设计：交互打点依赖对人物、物体、动作顺序和时间的理解。若第一步就把无声视频补成有声对话，或把采样帧之间的动作说成已看见，后面的“玩家在这里做什么”也会失去基础。

相对 v1：保留 summary、events、limitations 的事实输出，进一步说明“文件有音轨”不等于模型实际拿到或听清音频；静音/噪声可以没有音频事件，不按口型补台词；不为填满时间轴重复拆分动作。此版仍不产生交互点，因此它是事实基线，不是 Day 2 打点成品。现有 Day 2 对照报告没有可用于声称 v2 打点效果的数据。

v3：第一次把事件转为候选

为什么设计：Day 2 要从“描述视频”迈向“哪里值得玩家参与”。

相对 v2：新增必需的 interaction_points，最多两个；每点分开写 time_s（暂停位置）、action_start_s（片中相关行动起点）、visible_cue、player_action、reason、evidence、uncertainty。优先考虑动作前、可见选择前、关键物体成为行动线索时；允许空数组，不推荐小游戏或生成代码。

实际结果：固定 qwen3.8-flash、2 fps 抽帧的三次 S05/一次走廊实验中，走廊为空，但 S05 有过早打点、把准备认成已执行、误称投中等问题。v3 建立了可定位的交互点结构，尚未解决事件事实和动作起点识别。

v4：严格区分“暂停时所见”和“后来发生”

为什么设计：v3 容易把后来看到的动作或结果倒写成暂停当下已有的线索，也可能把普通镜头硬加为候选。

相对 v3：明确 time_s 应在可见准备之后、动作真正开始之前，原则上留约 0.5 秒；action_start_s 指球离手、触碰目标等执行起点，而非仅仅持球或抬手；证据只能引用暂停当时及之前所见，理由要具体，同一动作不重复打点。文本加入篮球例子解释“靠近篮筐≠投中、持球≠已投篮”，它是纠错例子，不是通用题材定义。

实际结果：同一组固定条件实验仍有过早候选、把接球/抬球误认作新的出手、误称得分。规则更清楚，并未令模型稳定遵守。

v5：只选最强一点，并索要三段顺序证据

为什么设计：v3/v4 一次可报两个点，输出中较弱的点常靠猜；需要验证“准备→尚未执行→执行”是否真的依次可回看。

相对 v4：上限降为一个，要求暂停位置取输入实际提供的采样画面时间戳；候选需分别指出准备画面、随后仍未执行的画面和真正执行的画面。更明确地禁止把接球、蓄力、举臂当作出手，宁可空结果。

实际结果：三次 S05只有一次较可用，一次原始 JSON 不合法，一次明显过早；走廊为空。限制减少候选数量，却没有证明更稳定或更真实。这里也暴露出“要求实际采样帧时间戳”不适合之后的整段直传模式。

v6：改为有声视频直传的任务描述

为什么设计：输入从顺序采样画面转到整段视频，并希望利用真实音轨辅助核实动作，不能继续要求“输入提供的采样帧时间戳”。

相对 v5：明确输入为整段视频，time_s 改为片内估计秒数；候选上限回到两个；候选新增 source=visual|both，声音只能辅助，不能单独触发打点；事件仍可按 visual|audio|both 标来源。背景谈话、噪声、音乐不自动成为交互机会，未听清不推断声音。

实际结果：Omni 直传、2 fps 的 7 次 v6 调用里，有声 S06 的 1.5 秒位置在 3 次中出现 2 次，用户认可该位置可玩；但对应“举拍”等文字证据与画面不符。有声/无声组均有漂移和空结果，走廊为空。位置可玩不能推成动作叙述正确，音频 Token 为正也不能证明声音改善了打点。

v7：进一步收紧三段状态与单点筛选

为什么设计：v6 有时位置接近可玩区，却错误描述人物持拍、挥拍和球路；想减少凭单帧或声音臆测的候选。

相对 v6：候选从最多两个缩为一个；要求同一主体的准备、至少约 0.5 秒后仍未执行、再到执行三个不同状态；要求大致覆盖开头、中段和末段，再选证据最强点。音频在动作后出现时只能核实动作，不能倒推出之前的准备。

实际结果：同样条件的 7 次 v7 调用中，有声 S06 三次为空、15.5 秒、空；唯一候选的三段画面依据也不足。更严使输出更少，没有证明留下的点更可靠；走廊继续为空。

v8：从特定动作规则转为通用“事件→机会”

为什么设计：v6/v7 的措辞高度围绕持拍、挥拍和球台，不适合用户上传的任意视频；同时需要先把事件时间线写具体，再让候选可追溯到某个事件。

相对 v7：不再专门讨论乒乓球；第一阶段细写主体/物体、前后状态、实际变化和结果是否可见，第二阶段只从这些事件中选最多一个动作前、可见分岔前或关键物体后的参与机会。reason 和 evidence 必须能对应事件。沿用严格的 time_s < action_start_s，故没有后续可观察行动的“纯发现物体/纯决定”只能写入事件，不能硬生成候选。

实际结果：Omni 的 S06 同条件三次均为空，且事件描述本身也有遗漏和误述；VL Plus 的 v8 三种输入条件在 S05 都给出第二次投篮附近候选，在 S06 都为空。三种输入条件各只一次，不能算三次同条件稳定性。现有证据支持“v8 在这些 S06 测试里召回不足”，不能断言仅由提示词造成，小目标/遮挡和模型时间理解也可能参与。

v9：跨题材 few-shot，并允许“只有准备、未见执行”

为什么设计：v8 把“后续动作必须拍到”当作统一门槛，可能错过人物已明显准备、但视频在执行前切走的机会；抽象规则也不足以教模型区分接球、发球、做饭、起跑等行为。

相对 v8：增加正反 few-shot：投篮、持具发球、做饭/起跑的“只见准备”，以及只有物体/空镜、动作后画面应为空。候选新增 action_observed：已看到相关行动时为 true 并给 action_start_s；只见明确准备时为 false、action_start_s=null，必须说明后续未拍到。仍最多一点，仍要求准备、证据、声画来源和不确定性。它扩展了可选机会的边界，却没有放开候选数量。

实际结果：Omni 固定条件 v9 实验在 S06 从 v8 的 0/3 有点变为 3/3 有点，但三次位置/人物漂移，具体姿态、击球依据多处不实；完整 v9 复盘还记录 S01 倒水 0/3 漏点，S05 只见准备 3/3 都误写为行动已发生，空走廊 0/2 正确。VL Plus 的 v8/v9 对照同样显示“原文出现候选”不等于通过结构或画面复核。few-shot 增加出点率的局部证据存在，识别质量提升尚未证实。

v10：通用“可观察事件→交互点”，反对静→动

最初的 v10 为什么出现

S07 长比赛片段被概括为“连续攻防、没有静止待发点”，于是 2026-10-20 的早期 v10 把“接应、接球、获得物体控制、接稳后的下一步处理”定义为控制权交接。相对 v9，它不再要求人物先静止：连续运动中若能辨出接收前或取得控制后的下一步，也可选一个点；并严格区分同一主体、同一轮事件链，防止把第一轮接球接到第二轮投篮。这个设计显著借用了篮球传接情境，容易让通用任务看起来偏球类。其原文完整保存在早期 v10 运行记录的 prompt 字段，而不是当前文件中。

当前 v10.txt 怎样不同

后来直接改写成通用“可观察事件→交互点”提示词，单独解释 time_s 是可点击定位，player_action 是玩家做什么，reason 是为什么；考虑动作前、可见选择和新发现且被强调的物体，不要求静止。它给出投篮、发球、起跑、驾驶、吃饭、做饭、路径分岔、发现物体和空镜等九类假设片段；仍最多一个候选，沿用 action_observed、来源、证据与不确定性字段。相对早期 v10，题材覆盖更广；相对 v9，交互点定义和定位字段的职责更明确，但文本也更长、约束仍多。

记录如何解读

早期 v10 的 S05/S06/S07 运行与后来使用当前文本的运行，虽然都标为 prompt_file=prompts/v10.txt，prompt 全文并不相同，不能合并为一个 v10 重复实验。例如后来的一次 S05 记录才与当前文件一致。若比较效果，必须以每条 JSON 保存的实际 prompt 为准。现有材料不足以证明当前 v10 在跨题材上优于 v9。

v12：降低候选门槛，重新聚焦“发现机会”

为什么设计：前几版为防误判不断增加“准备—未执行—执行”、证据、来源、结果可见性等门槛；在已有 S06、S01 实验中出现了明明可以讨论玩法入口却返回空点的情况。用户明确把 Day 2 目标调整为先找出任何与视频事件相连、可让玩家参与的位置，后续再由人工或另一阶段筛选。

相对当前 v10：保留“先描述视频、再找机会”，但输出缩成 summary、简单 events、不限数量的 interaction_points[{time_s,opportunity,reason}]；不再要求 action_start_s、action_observed、source、evidence、uncertainty，不把动作前或后续行动出现设为唯一入口。明确普通镜头或动作结束后也不自动排除：只要提出具体参与和理由即可；仍可返回空数组。另加 7 组假设 few-shot，涵盖传接与投篮、发球、跑步、开车、做饭/吃饭、发现信件与选门、无变化墙面，展示同片多个点和空结果。它不是承诺所有点都正确，而是把本阶段从“严筛一个合格点”改为“开放提出候选”。

实际结果：两个模型的六份 v12 记录全部成功并有候选：S05、S06、S07 各由 Omni 直传 1 fps 和 VL Plus 抽帧 1 fps 运行一次，共 23 个候选。画面复核仍发现 S05 的动作错配、S06 同时间位置却提出不同动作、S07 的开场事件/主体错误。候选数量增加是已观察到的现象；正确性、跨题材泛化、空镜误报率和重复运行稳定性未获证明。两个模型的输入模式和音频条件也不同，不应用这六次运行直接排名模型。

03 / NOTES优化认识

  1. 任务定义发生了转向。v3–v10 主要尝试让模型一次完成“理解＋严格验证＋只选最佳点”；v12 则先扩大机会发现范围，把是否用于后续游戏留给人工或后续筛选。两种版本追求的指标不同，不能只用“有点率”判胜负。
  2. 事实错误不会靠加长提示词自动消失。多版都出现人物/动作/结果的误述；严格版可能减少候选，开放版可能放大联想。核心评估要把事件真实性、位置可玩性和建议理由的真实性分开记录。
  3. 可定位是必要条件，不等于精确到帧。time_s 是原片的点击回看位置；模型在 1–2 fps 或直传采样下可能有时间误差，仍须回看附近连续画面。位置接近，不代表模型说的动作一致。
  4. 下一轮需同条件比较。固定模型、输入方式、fps、素材，对 v12 重复运行，并补空镜及非运动视频；对每个点标注“位置可玩/理由吻合/仅为创意延伸/事实错误”。若探索第二阶段 AI 筛选，最好让它连原画面一起复看，而不是仅继承第一阶段可能失真的事件文字。
