# 视频分析器 · Day 01–02

上传或选择视频，由多模态模型记录可观察事件，并寻找适合暂停让玩家参与的候选位置。当前只实现候选打点；小游戏选择和 JS 试玩尚未实现。模型判断须回看原片，不能把打点或文字依据直接当作已验证事实。

## 目录

```
demo/                 本地工作台：后端、网页、测试
prompts/              v1–v9 版本提示词
mp4-example/          页面可直接选择的 MP4 样例
day2/                 Day 2 标注、素材来源、实验报告与复核图
results/<模型名>/      每次调用的完整原始 JSON（含失败记录）
docs/day1/            Day 1 模型测评和工作汇报
docs/技术实习生_梁玉龙_新人任务书.html   原始任务书
README.md             本说明
.env                  本机密钥及模型配置，不要公开
```

`results/` 下按模型分文件夹，历史 JSON 的内容没有改动，只调整了保存位置。新记录也写入 `results/<模型名>/`。`BEEROUTE_MODELS` 里的模型会出现在网页下拉框；修改 `.env` 后重启 Demo。

## 启动

需要 Python 3.10+ 和 FFmpeg（含 ffprobe），二者在 PATH 中。代码只用标准库。

1. 在项目根目录运行 `python demo/app.py`。
2. 打开 http://127.0.0.1:8765 。
3. 从 `mp4-example` 选择一条视频，或上传不超过 60 秒、12 MiB 的 MP4。
4. 选择提示词版本、顺序抽帧或直接传视频，点击分析。
5. 成功或失败的记录都写入 `results/<模型名>/`。候选交互点和事实事件分开展示，都可点击回看原片；空候选会明确显示。

页面列出 `prompts/` 中的所有 `vN.txt`，当前默认选 v6；可以手动选 v9 做跨场景 few-shot 实验。非页面调用未指定版本时使用数字最高版。v9 曾按用户要求直接修订；每份记录保存调用时实际使用的提示词全文和版本，旧记录不受影响。

Day 2 的 `analysis.interaction_points` 是必需数组，v7 起最多一项；空数组表示没有可靠候选。`source=visual` 表示仅画面，`source=both` 表示声画共同依据且要求已确认音频 Token，不接受纯音频候选。v9 增加 `action_observed`：行动已拍到时须有片内 `action_start_s` 且打点在其之前；明确准备但行动未拍到时允许 `action_start_s: null`。旧记录仍按原字段读取。结构校验不等于画面事实核实。

实验按顺序查阅：[早期 v3–v5 复盘](day2/report.md)、[有声视频 v6–v7 对照](day2/omni-direct-report.md)、[v8 乒乓球](day2/v8-single-video-report.md)、[v8 篮球/乒乓球](day2/v8-s05-s06-comparison.md)、[v9 跨场景复盘](day2/eval/v9/report.md)。最后一次 v9 的 16 次调用提高了出点数量，但事实依据和准备/执行边界仍不可靠，不能宣称已稳定完成自动打点。

素材许可、哈希和人工标注保存在 `day2/` 及 `day2/eval/v9/`。人工标注只用于评估，不是 Demo 运行的前置步骤。

直接传视频时，仅对支持视频音频的模型（当前为 Gemini 与 qwen3.8-omni-flash）尝试分析音轨。其他模型即使原视频含音轨，也会收到临时生成的无音轨副本；原视频不变。抽帧始终没有声音。只有服务返回正数音频 Token 时，才接受音频事件。模态用量明确没有图像或视频 Token 时，直传结果记为失败；服务不提供模态明细时保留结果，并标注无法核实视频是否进入模型。

`qwen3.8-omni-flash` 直传优先请求 JSON Object 输出；仅当网关明确拒绝该参数时才去掉参数重试一次，记录中保留两次尝试。v9 的 16 次均无需回退。

```
python -m unittest discover -s demo/tests -v
```
