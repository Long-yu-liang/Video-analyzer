# 视频分析器 · Day 01–03

上传或选择视频，由多模态模型记录可观察事件，寻找适合暂停让玩家参与的候选位置，再从预设小游戏里推荐玩法。用户可以调整暂停时间，并接受、修改或放弃推荐。当前不生成、也不运行 JavaScript。模型判断须回看原片，不能把打点、推荐或文字依据直接当作已验证事实。

## 目录

```
demo/                 本地工作台：后端、网页、测试
prompts/              旧版 vN.txt；v13/、v14/ 为两阶段提示词；v15/gameplay.txt 为玩法推荐
prompts/games/        预设小游戏目录
mp4-example/          页面可直接选择的 MP4 样例
day2/                 Day 2 版本历程、模型对照和两阶段复盘；旧报告存入 archive/
day3/                 小游戏类型说明，以及 S07 的玩法选择记录
results/<模型名>/      每次调用的完整原始 JSON（含失败记录）
day1/                 Day 1 测评、工作汇报和原始任务书
README.md             本说明
.env                  本机密钥及模型配置，不要公开
```

`results/` 下按模型分文件夹，历史 JSON 的内容没有改动，只调整了保存位置。新记录也写入 `results/<模型名>/`。`BEEROUTE_MODELS` 里的模型会出现在网页下拉框；修改 `.env` 后重启 Demo。

## 启动

需要 Python 3.10+ 和 FFmpeg（含 ffprobe），二者在 PATH 中。代码只用标准库。

1. 在项目根目录运行 `python demo/app.py`。
2. 打开 http://127.0.0.1:8765 。
3. 从 `mp4-example` 选择一条视频，或上传不超过 60 秒、12 MiB 的 MP4。
4. 提示词单独列出，事件识别、机会发现、玩法推荐各自选择一个已有版本，默认用该步骤的最高版本。模型、输入方式（直接视频或顺序采样）和采样率用于第一步事件识别，后两步沿用所选模型。下方可展开查看三份提示词全文。第一步识别事件并供用户逐条回看、取消勾选失实事件；第二步发送所选事件的对应画面。事件识别选 v14 时，超过 25 秒会按约 20 秒分段、相邻片段重叠约 1 秒，必要时对截断片段缩短重试，因此可能产生多次计费调用。「刷新重置」恢复到刚打开页面时的选择和空白结果。
5. 成功或失败的记录都写入 `results/<模型名>/`。候选交互点和事实事件分开展示，都可点击回看原片；空候选会明确显示。

页面不再提供旧的单次分析。`/analyze` 仍接受 `prompts/` 中的 `vN.txt`，未指定版本时使用数字最高版。事件、机会和玩法提示词按 `prompts/vN/` 下的文件分别选择，不再把 v13 或 v14 绑成唯一流程。v14 的分段只在事件识别选中 v14 时发生。版本均保留，不覆盖旧文件。各步结果分别保存，通过记录 ID 关联；后一步重新提交同一视频并校验 SHA-256，不长期保存上传的视频副本。

第三步使用 [prompts/v15/gameplay.txt](prompts/v15/gameplay.txt) 和 [prompts/games/catalog.json](prompts/games/catalog.json)，只在点击物体、剧情选择、时机操作、连点和拖拽里为已有交互点推荐玩法。用户可以改暂停时间，并接受、修改或放弃；原始画面时间保留。保存玩法描述不再调用模型，记录阶段为 `gameplay_brief`。放弃的点仍留在记录里，下一步只使用接受或修改后的条目。试玩尚未实现。类型说明见 [day3/小游戏类型说明.md](day3/小游戏类型说明.md)，S07 的一次真实推荐和取舍见 [day3/S07-玩法选择记录.md](day3/S07-玩法选择记录.md)。

Day 2 的 `analysis.interaction_points` 是必需数组。现存旧版 v3–v10 使用逐版收紧的候选结构，v7–v10 最多一项；v9–v10 要求 `action_observed` 与相应的 `action_start_s`。v12 改为不限候选数量，每个点只需要片内 `time_s`、`opportunity` 和 `reason`；事件只需起止时间和描述。页面兼容新旧记录。结构校验只保证格式和定位时间有效，不代表模型建议一定合理。

Day 2 可从[提示词 v2–v12 优化历程](day2/提示词v2-v12优化历程.md)、[v12 双模型分析](day2/v12-双模型交互点分析.md)、[v13 两阶段验证与复盘](day2/v13-两阶段验证与复盘.md)、[v14 S07 分段验证](day2/v14-s07-分段识别验证.md)进入。v8/v9 的[VL Plus](day2/qwen3-vl-plus-v8-v9-交互点处理.md)与[Omni](day2/qwen3.8-omni-flash-v8-v9-交互点处理.md)对照仍保留，早期报告和标注在 `day2/archive/`。v13 对四段视频各重复两轮，共 16 次真实调用；v14 的 S07 分段调用解决了输出截断，但事实依据仍须逐点复核。

素材许可、哈希和人工标注保存在 `day2/archive/`，实验视频与复核图片保存在 `day2/source/` 和 `day2/eval/v9/`。人工标注只用于评估，不是 Demo 运行的前置步骤。

直接传视频时，仅对支持视频音频的模型（当前为 Gemini 与 qwen3.8-omni-flash）尝试分析音轨。其他模型即使原视频含音轨，也会收到临时生成的无音轨副本；原视频不变。抽帧始终没有声音。只有服务返回正数音频 Token 时，才接受音频事件。模态用量明确没有图像或视频 Token 时，直传结果记为失败；服务不提供模态明细时保留结果，并标注无法核实视频是否进入模型。

`qwen3.8-omni-flash` 直传优先请求 JSON Object 输出；仅当网关明确拒绝该参数时才去掉参数重试一次，记录中保留两次尝试。v9 的 16 次均无需回退。
