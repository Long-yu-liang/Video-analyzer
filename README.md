# 视频分析器 · Day 01–03

上传或选择视频，由多模态模型记录可观察事件，寻找适合暂停让玩家参与的候选位置，再从预设小游戏里推荐玩法。用户可以调整暂停时间，并接受、修改或放弃推荐。当前不生成、也不运行 JavaScript。模型判断须回看原片，不能把打点、推荐或文字依据直接当作已验证事实。

## 目录

```

prompts/              旧版 vN.txt；v13/、v14/ 为两阶段提示词；v15–v20 为玩法推荐版本
prompts/games/        预设小游戏目录
mp4-example/          页面可直接选择的 MP4 样例
day2/                 Day 2 版本历程、模型对照和两阶段复盘；旧报告存入 archive/
```

`demo/` 根目录的 `projects.py`、`output_contract.py`、`gameplay_*.py` 仅保留兼容导入，实际实现位于上面的功能包。新功能应修改对应模块，不把业务代码继续写回兼容入口。`app` 与后端应用共享同一运行时状态，旧测试和脚本的调用方式仍可使用。

静态资源使用 `/assets/…`；旧 `/workbench.js`、`/workbench.css` 和 `/gameplay-*.js` URL 保留映射。目录整理不改提示词、模型参数、视频限制、记录格式和分析逻辑，也不移动 `results/`、`projects/` 或素材。

常用工具新路径：

- `python demo/tools/evaluation/evaluate_v20_batch.py --help`：查看批次实验选项，`--run` 会计费，不能用于普通目录检查。
- `python demo/tools/evaluation/analyze_v20_batch.py --help`：查看离线分析选项。
- `python demo/tools/recovery/revalidate_opportunities.py <record_id>`：仅本地复核并另存派生记录。
- `python demo/tests/fixtures/workbench_browser_fixture.py`：启动 8768 端口的无计费界面夹具。

`results/` 下按模型分文件夹，历史 JSON 的内容没有改动，只调整了保存位置。新记录也写入 `results/<模型名>/`。`BEEROUTE_MODELS` 里的模型会出现在网页下拉框；修改 `.env` 后重启 Demo。

新结果按 `S06_有声乒乓球__frames__20261022_第一步.json` 命名：事件识别为第一步、机会发现为第二步、玩法推荐为第三步；保存选择为“玩法描述”，旧单阶段接口为“单阶段分析”。日期按北京时间取保存日期，同日重名追加 `_2`、`_3`。步骤关联使用 JSON 内的 `record_id`，旧文件仍可读取，无需重命名。

v19 的九次真实调用及未达标原因见 [历史对照验证与选择记录](day3/v19-对照验证与选择记录.md)。当前 v20 将重心恢复为推荐玩法，不再把固定暂停方式、坐标和参数当作推荐门槛；本次调整没有新增计费实验，不能据此声称推荐质量提高。

## 启动

需要 Python 3.10+ 和 FFmpeg（含 ffprobe），二者在 PATH 中。代码只用标准库。

1. 在项目根目录运行 `python demo/app.py`。
2. 打开 http://127.0.0.1:8765 。
3. 从 `mp4-example` 选择一条视频，或上传不超过 60 秒、12 MiB 的 MP4。
4. 提示词单独列出，事件识别、机会发现、玩法推荐各自选择一个已有版本，默认用该步骤的最高版本。模型、输入方式（直接视频或顺序采样）和采样率用于第一步事件识别，后两步沿用所选模型。下方可展开查看三份提示词全文。第一步识别事件并供用户逐条回看、取消勾选失实事件；第二步发送所选事件的对应画面。事件识别选 v14 时，超过 25 秒会按约 20 秒分段、相邻片段重叠约 1 秒，必要时对截断片段缩短重试，因此可能产生多次计费调用。「刷新重置」恢复到刚打开页面时的选择和空白结果。
5. 成功或失败的记录都写入 `results/<模型名>/`。候选交互点和事实事件分开展示，都可点击回看原片；空候选会明确显示。

页面不再提供旧的单次分析。`/analyze` 仍接受 `prompts/` 中的 `vN.txt`，未指定版本时使用数字最高版。事件、机会和玩法提示词按 `prompts/vN/` 下的文件分别选择，不再把 v13 或 v14 绑成唯一流程。v14 的分段只在事件识别选中 v14 时发生。版本均保留，不覆盖旧文件。各步结果分别保存，通过记录 ID 关联；后一步重新提交同一视频并校验 SHA-256，不长期保存上传的视频副本。

第三步默认使用 [v20](prompts/v20/gameplay.txt)，重点是“这个场景适合怎么玩、玩家做什么、为什么适合”。从七种预设类型中每点最多给两个不同玩法，不设类型优先顺序；用户可接受、编辑或自行设计，也可放弃。成功、失败与反馈先用概念说明，具体秒数、按钮、坐标和运行规则在选定玩法后再细化；是否暂停或接回原片不作为推荐条件。画面事实应真实，设想的下一步无需与录像后续一致。没有推荐可以返回空。

v20 推荐与选择记录使用 `schema_version: 3`，不生成模板参数、框选要求、固定恢复播放策略或“代码生成就绪”标记。调整画面位置会按新位置送入图片并保留实际时间；位置变更后需重新推荐，失败保留草稿。保存选择仍不调用模型。图像base64只存在于模型请求中；新v19/v20记录使用独立JPEG文件、`frame_file`、时间与SHA-256，不把图片编码写进JSON。旧内嵌预览记录保留并兼容读取。v19可选作历史规则设计，见[历史规范](day3/小游戏模板与玩法描述规范.md)。试玩尚未实现。

Qwen非思考请求现在优先发送 `response_format: {"type":"json_object"}`。它约束JSON语法，不保证字段结构；当前视觉输入不宣称支持模型侧严格JSON Schema。v20同时保存并发送字段Schema说明，本地严格检查玩法的点ID、类型及核心文字；`abstentions` 的类型、缺少理由、重复或冲突问题单列 `analysis.warnings`，保留合法玩法。明确引用未知点仍会失败。错误携带字段路径，原始响应不修改。仅当网关以400/422明确拒绝JSON模式时，记录原因并回退一次；其他错误不自动重试。离线修复验证见 [重放结果](day3/eval/v20-format-fix/replay.json)，不改写原实验统计。

第二步现在按候选逐条检查：未知/未审核画面 ID、错误类型、缺少机会或理由、完全重复项会单列 `analysis.warnings` 并跳过，其他合法候选继续显示；不猜测 ID、不按顺序改绑画面。空数组仍表示未提出机会；非空但全部无效会明确失败，不能伪装成正常空结果。事件及旧版玩法的结构错误也带字段路径，非法 JSON 显示行列位置；视频哈希、时间范围及核心玩法校验不取消。这部分容错修改不改变提示词；后续新增的 v21 输入改进见下文。

机会发现新增 [v21](prompts/v21/opportunities.txt)，在 v15 的玩法思路上专门改善画面 ID 引用：不再给可直接照抄的固定编号，强调原样复制实际图片标签；请求附带本次允许 ID 与字段 Schema，并且先前事件上下文只包含本次审核保留的事件。该 Schema 是文本约定加本地校验，不宣称模型侧严格约束，也不能保证零错号或严格隔离后续画面。v15 及其他旧版提示词、输入策略保留，方便复现；第一步和第三步不变。页面按步骤选择最高版，重启并刷新后机会发现默认 v21，已保存项目仍恢复自己记录的版本。本次仅做本地模拟测试，未新增计费验证，不宣称模型效果已改善。

已有第二步失败响应可用 `python demo/tools/recovery/revalidate_opportunities.py <record_id>` 做本地复核，另存 `record_kind: local_revalidation` 的派生记录，可通过工作台导入。其 `model_call_made: false`、`usage: {}`，不计作新模型实验；原始记录、响应、用量及失败状态不改。只有原调用正常结束、审核映射完整且至少保留一个合法候选时才能恢复；内容是否真实仍需回看，结构通过不代表事实通过。

Day 2 的 `analysis.interaction_points` 是必需数组。现存旧版 v3–v10 使用逐版收紧的候选结构，v7–v10 最多一项；v9–v10 要求 `action_observed` 与相应的 `action_start_s`。v12 改为不限候选数量，每个点只需要片内 `time_s`、`opportunity` 和 `reason`；事件只需起止时间和描述。页面兼容新旧记录。结构校验只保证格式和定位时间有效，不代表模型建议一定合理。

Day 2 可从[提示词 v2–v12 优化历程](day2/提示词v2-v12优化历程.md)、[v12 双模型分析](day2/v12-双模型交互点分析.md)、[v13 两阶段验证与复盘](day2/v13-两阶段验证与复盘.md)、[v14 S07 分段验证](day2/v14-s07-分段识别验证.md)进入。v8/v9 的[VL Plus](day2/qwen3-vl-plus-v8-v9-交互点处理.md)与[Omni](day2/qwen3.8-omni-flash-v8-v9-交互点处理.md)对照仍保留，早期报告和标注在 `day2/archive/`。v13 对四段视频各重复两轮，共 16 次真实调用；v14 的 S07 分段调用解决了输出截断，但事实依据仍须逐点复核。

素材许可、哈希和人工标注保存在 `day2/archive/`，实验视频与复核图片保存在 `day2/source/` 和 `day2/eval/v9/`。人工标注只用于评估，不是 Demo 运行的前置步骤。

直接传视频时，仅对支持视频音频的模型（当前为 Gemini 与 qwen3.8-omni-flash）尝试分析音轨。其他模型即使原视频含音轨，也会收到临时生成的无音轨副本；原视频不变。抽帧始终没有声音。只有服务返回正数音频 Token 时，才接受音频事件。模态用量明确没有图像或视频 Token 时，直传结果记为失败；服务不提供模态明细时保留结果，并标注无法核实视频是否进入模型。

`qwen3.8-omni-flash` 直传优先请求 JSON Object 输出；仅当网关明确拒绝该参数时才去掉参数重试一次，记录中保留两次尝试。v9 的 16 次均无需回退。

## 项目工作台（功能扩展，不改变模型策略）

顶部可命名、保存、新建或打开项目。编辑自动保存，也可手动重试；保存冲突不会覆盖其他窗口的新版本，可选择“另存副本”。项目在本机 `projects/<安全ID>/` 保存当前文件及修订快照，原始 `results/` 不修改。上传视频恢复后需重新选择同一文件并匹配 SHA-256；样例自动核对。未提供匹配视频时仍可编辑文字，但不能继续模型请求。草稿备份可以通过导入入口恢复为独立项目。

三个视图为“分析与选点”“玩法比较与编辑”“编排与描述预览”。顶部可选择 `results` 中任一步的原始 JSON，按记录 ID 导入其关联结果，不提交文件到模型。时间轴可回看；人工新增、放弃和合并只作用于项目草稿。恢复项目或导入时只载入关联摘要，完整原始响应保留在显示的 `record_file` 文件中。每点的不同推荐版本分别保留，重新推荐必须主动确认并计费，仍走原有请求流程；人工新增点不送入模型。旧批次点需恢复对应分析状态后才能重推荐，当前版本不跨批次自动切换。

选中玩法后可人工补充新增画面元素、判定规则和视频衔接，确认描述，再在编排清单启用。改点位或关键内容会撤销确认，旧方案保留并提示核对。“全部草稿”与“已确认且启用方案”分别导出；同一时间多个启用项、未确认或失效项不能导出为确认集合。确认仅表示设计已整理，不表示已生成代码或通过试玩。顶部草稿备份可在保存失败时下载当前编辑内容。

本轮不修改提示词、模型、输入构造、抽帧、参数和推理结果校验，也不自动发起真实调用。单点推荐只是原有第三步选择一个点；新界面不自动填充游戏规则。不生成或运行 JS。

本地项目测试：`node demo/tests/frontend/workbench_model.js`。浏览器零计费夹具：`python demo/tests/fixtures/workbench_browser_fixture.py`，访问 `http://127.0.0.1:8768`；其中所有分析均为明确标注的模拟数据，项目写入系统临时目录，不写入正式实验结果。
