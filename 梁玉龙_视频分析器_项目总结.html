项目总结与技术复盘

视频分析器项目总结

五阶段实施过程、模型选择、提示词演进与问题解决

作者：梁玉龙整理日期：2026年10月27日阶段：原型收尾

一 项目目标与最终成果

本项目围绕《技术实习生 · 练手任务书》中的“视频分析器”展开：用户给出一段视频，AI 识别画面发生的事件，寻找适合玩家参与的位置，结合预设小游戏类型推荐玩法，再把用户选定的方案生成 JavaScript，放回视频中试玩。

我完成的核心工作，是把视频理解、交互构思、玩法选择、代码生成和运行反馈连接成一个可以反复使用的工作台。用户可以查看 AI 的判断、调整位置、修改方案、只生成自己需要的游戏，并在同一个项目中保存版本和试玩问题。

最终体验采用“原视频暂停 → 叠加小游戏 → 显示结果反馈 → 继续原视频”。玩家操作影响小游戏的结果，原视频继续播放已经拍摄的内容。这个实现范围使项目能够先把视频与交互衔接跑通，避免把角色像素编辑、剧情分支或重新生成视频混入本轮目标。

对照任务书，目前已经具备完整的演示流程、模型体验与选择记录、提示词优化历程、真实生成产物和调试资料。项目仍需要用户回看事实、判断玩法和实际试玩；完整流程成立，不代表任意视频都能一次生成准确且好玩的游戏。

二 完整流程如何工作

1 视频分析

用户选择本地 MP4，配置模型、直接视频或顺序抽帧输入。第一步只记录可观察事件，包括动作起止、代表画面时间、具体描述、画面依据和不确定性，不在这一阶段同时设计玩法。

直接视频保留了视频输入形式，但模型实际如何采样由接口和服务端决定；顺序抽帧由程序明确提供图片及时间戳，适合核对送入了哪些画面。两种输入都保留，依据素材和部署表现选择，不能把抽帧描述成完整连续视频，也不能把视觉输入当成已经获得声音。

2 寻找交互机会

用户回看事件并选择需要继续分析的画面。第二次调用接收这些事件和对应图片，说明玩家可以参与谁的行为、控制哪个环节，以及为什么这个位置适合参与。

机会可以来自准备动作、取得物体、发现目标、面对不同方向，或者仍可参与的动作过程。新的参与行为可以不同于实拍后续，但应明确是设计设想。模型引用输入画面的 ID，程序再把它映射为实际抽取时间，减少模型重新编造定位秒数的问题。

用户明确选入的交互点才进入后续流程，也可以调整时间、人工新增或删除不合适的点。人工修改与原始模型结果分别保存。

3 推荐和选择玩法

第三次调用读取交互机会、当前对应画面和预设目录，推荐最多两个有实际差异的方案。每个方案说明场景关系、玩家目标、操作、成功失败条件和反馈；没有合适玩法时允许明确不推荐。

用户可以比较方案、打开独立描述弹窗进行编辑，或者自行设计一个新方案。推荐阶段先回答“这里怎么玩”，详细数值、控件布局等实现内容留到选定方案后补全。

4 单点生成游戏

每个已选玩点有自己的生成入口。点击某一个点，只提交该点当前采用的文字方案，由 MiniMax 一次补全详细设计并生成 JS、CSS，不把所有点一起生成，也不再次发送视频或图片。

模型输出经过结构和 JavaScript 语法检查，页面展示设计及版本。生成任务在本地服务后台执行，切换页面或刷新不会自动重新发起同一次生成；任务列表展示状态、已等待时间和失败原因。

5 视频交互编排与试玩

用户选择每点采用的游戏版本，设置是否参与播放。在大屏中查看视频和简单时间轴，到达可用交互点时暂停原片并启动游戏，反馈后继续播放；也可以只试玩某一个点。

小游戏运行在独立 iframe 中。宿主管理视频、挂载、退出、错误和续播；生成代码只负责容器内的输入、控件和判定。项目保存草稿、版本选择及运行记录，重新打开后匹配原视频即可继续工作。

四 模型为什么这样选择

1 先用相同素材认识模型差异

Day1 阶段报告记录了四个模型、两种输入方式、四段素材，共 32 次调用。测试使用相同提示词和 1 fps 设置，比较输出细节、时间定位、响应速度和用量。这个数字是当时阶段报告的统计，不是当前结果目录总量，也不表示 32 次事实判断全部正确。

模型当时样本中的主要表现对后续选择的影响
gemini-2.5-flash-lite响应较快，但抛接球直传样例出现大量重复事件，部分身份和声音表述待核实速度有吸引力，仍需要检查重复生成和事实可靠性
qwen3-vl-plus人物、物体及画面文字描述较细，响应相对慢，也存在动作阶段和主体误认作为后续视觉事件、机会与玩法分析的重要实验模型
qwen3.8-flash速度与描述详细程度较均衡，部分声音和意图判断偏推测保留为对照选择，不能把快速返回当成理解准确
qwen3.8-omni-flash用于探索有声直传；早期声音结论存在疑似漏检，后续声画实验需要核验音频任务单独验证，不因名称包含 Omni 就认定听懂了声音

这些结论来自当时的素材和通道。没有统一人工真值时，我没有把事件数量、格式成功或多个模型说法一致直接换算成准确率，也没有据此给出适用于所有视频的模型排名。

2 按阶段输入决定模型职责

视频事件识别需要视觉或视频能力；机会发现和玩法推荐仍然发送图片，也需要能够读取画面的模型。把它们换成纯文本模型，会改变输入和判断依据，应作为另一个实验。

代码生成阶段已经有用户选定的单点方案，主要任务变成细化规则和编写 JavaScript，因此接入 MiniMax 处理文字实现。这样既减少重复发送媒体，也让两类问题容易区分：前序模型是否看懂画面，以及生成模型是否实现了给定设计。

选择 MiniMax 是本项目的实现分工和真实接入尝试，不是经过同条件代码生成评测后证明它优于所有其他模型。前面三次分析也不要求必须采用三个不同型号；拆分任务的价值首先在于结果可检查、可编辑、可追踪。

3 内网部署需要重新验证参数

收尾阶段接入 Qwen3.8-Flash-Next 后发现，之前的调用经验不能直接照搬。关闭思考的参数位置、输出额度和网关超时会明显影响表现。即使名称同属 Qwen，不同服务也可能接受不同参数。

最终增加了可配置的分析输出额度、思考模式、思考参数位置和玩法批次。模型名称原样传给接口，家族识别忽略大小写；实际请求和返回用量写入记录，以运行证据判断设置是否生效。

五 提示词如何逐步优化

1 从描述视频到定义交互机会

最初先建立事实描述基线，避免模型补写对话、身份、动机和未看清的结果。随后尝试严格的动作前打点：要求准备线索、动作起点、时间先后、证据和不确定性，并限制候选数量。

这些要求是为了减少误判，但也使机会发现变得过窄。部分视频只有连续动作或准备状态，模型会因没有完整拍到后续执行而返回空；继续增加规则也没有稳定解决人物和动作识别错误。

v8、v9 开始强调通用事件和跨题材示例，允许只拍到准备、未拍到执行的情况。实践又发现，示例过于集中会引导模型偏向篮球、发球等题材。之后将任务重新概括为：说明发生了什么、哪里适合玩家参与、为什么适合，而不是只寻找某一种运动的标准起手姿势。

v12 放开候选数量，降低过早筛选的门槛。在当时 S05、S06、S07 的六次双模型运行中，共产生 23 个候选，但复核仍发现动作错配和依据不实。这让我认识到，“有交互点”只是候选发现的起点，不能代替是否真实贴合画面的判断。

2 v13 和 v14 改变的是工作方式

v13 将一次完成的任务拆成“先识别事件，再寻找机会”。第一阶段的事实可以先回看，第二阶段拿着对应原图提出参与行为。错误因此更容易定位，也为用户保留了中途取舍的空间。

v14 继续扩大通用事件观察范围，区分准备、执行、持续和结束，关注物体、方向、人物关系及局部操作。同时配合程序分段解决长视频描述写不完的问题。提示词负责描述要求，程序负责分段、时间换算和结果合并，二者不能混为单纯的提示词效果。

3 玩法推荐经历了过度限制和重新放开

v15 建立第三步推荐；v16 引入更多示例和操作类型。因为模型容易把参与都写成“选择投、传、运”，v17 一度禁止 choice，v18 恢复但降低其优先级。

这段尝试说明，直接禁止一种玩法会改变分布，却不一定得到更合适的建议。v19 又将完整实现规则、暂停方式和标注过早放到推荐阶段，字段多、约束重，反而干扰“这里可以怎么玩”。v20 回到玩法构思，具体规则留到用户选定之后。

后续版本继续补充画面 ID 绑定、图文冲突处理和逐点覆盖。当前事件与机会使用 v22，玩法推荐使用 v23；七种玩法按情境匹配，不再固定把 choice 当作备选。最新分析提示词去掉了素材型 few-shot，保留任务职责、输入身份和输出契约，减少对某类素材的引导。

4 游戏生成提示词独立迭代

生成与修复提示词放在 prompts/game-generation/，不与事件分析混用。早期建立单点输入和 mount(container, api) 协议，后续增加 DOM 引用、取消输入、计时坐标、结束与销毁的自检要求。

仅要求“输出合法 JSON”仍反复出现非法转义，因此后续把设计保留为 JSON，JS 和 CSS 改用独立原文分段。当前 v5 进一步要求设计段完整非空，并与代码实际规则一致。它减少了把长代码嵌入 JSON 字符串的转义负担，但标记缺失、输出截断和运行错误仍需要程序检查及试玩发现。

六 从交互建议到小游戏的设计工作

我把玩家操作整理为七类，供推荐、编辑和生成共用，避免每一步使用不同名称和解释。

类型玩家实际参与的内容设计时需要说清楚的重点
tap_object 点击物体指认或点击目标点谁、为什么点、如何确认点中
choice 剧情选择在不同方案中取舍选项的情境依据与实际差异
timing 时机操作在合适时刻触发操作窗口及过早、过晚的结果
hold_release 按住后松开控制积累程度与释放程度如何变化、何时释放合适
mash 连点持续施力或累计推进次数、时限、反馈和未完成条件
drag 拖拽移动对象并对准目标拖动对象、落点和释放判定
swipe 短滑表达一次方向输入方向、距离和取消操作

类型只是操作语义，玩法还需要目标。例如投篮画面中的蓄力、抛球力度、起跑连点可以使用相似输入，但参与目的和反馈应与画面相关。同一画面也可能支持不同体验，不能只替换按钮文案就算一个新方案。

我把设计分成两层：推荐阶段用简洁文字说明参与意图；生成阶段再补控件、默认数值、状态转换和结束条件。这样既保留创作空间，也能在真正实现时得到可计算的规则。

七 项目难点及解决过程

1 模型描述错误会逐步传到玩法

篮球“已经持球”被描述成“等待接球”，球已离手仍被推荐蓄力，小球或多人画面中的持物者被认错，都会使后续方案偏离目标。给下一步传图能够提供复核材料，但不会自动纠正上游文字。

我通过拆分阶段、保留画面和事件关联、允许排除错误事件、调整点位以及编辑独立方案，让错误能够被发现和修正。新的玩法设想与视频事实明确区分；当前依然需要回看主体、物体关系和动作阶段，不能宣称这个问题已被提示词完全解决。

2 输出格式、辅助字段和核心引用需要区别处理

历史玩法响应曾把不推荐原因写成字符串数组，而程序要求对象数组；也出现缺少 limitations 的情况。如果所有字段同等严格，辅助说明的一处问题会拖垮已经合法的玩法。

我补清输出字段约定，并将兼容处理与模型原文分开记录。缺少部分辅助项时可以补默认值或记录警告；时间、对象 ID、核心玩法描述仍严格检查。第二步引用未发送的画面时，只剔除无效候选并保留其他合法项，不擅自把错误 ID 绑定到另一张图。

当前分析主要使用 JSON Object、提示词约定和本地业务校验。JSON Object 不等于模型侧严格 JSON Schema，更不保证画面判断准确；网关明确不支持格式参数时，回退及原因也需要保留。

3 视频能播放不代表模型输入和预处理一定成功

长片曾因整段事件描述达到输出上限而截断；较短尾段又遇到视频接口“文件太短”。本地也出现过 FFmpeg 抽帧失败，而原视频仍可播放。

我分别处理这些问题：将长片分段并换算回原片时间；适度重叠切点，降低边界遗漏；将过短尾段并入前段，整段过短时在调用前改用抽帧；区分预处理失败与模型失败。部分片段失败时，保留已完成事件、失败区间和实际用量，允许用户选择有效部分继续，不冒充全片完成。

上传限制扩展到 120 秒、30 MiB，并同步检查请求体和抽帧数量。更长原片先裁剪或分段，扩大本地限制不能代替模型接口限制。FFmpeg 间歇性错误通过工具路径配置及本机兼容版本复测处理，后续仍保留具体错误信息用于排查。

4 生成代码存在格式、运行和体验三个层次的问题

Invalid \\escape 发生在解析模型返回内容时，不能直接认定为 JS 算法错误。除了改用代码原文分段，我保留原始失败、缺失标记和截断信息，让下一轮修复获得具体上下文；只对边界清晰的格式兼容读取，不随意改写源代码冒充成功。

Cannot read properties of undefined (reading 'classList') 则属于运行时错误：数据对象没有正确绑定 DOM 元素，语法检查无法发现。对此在生成自检中加入引用初始化要求，在试玩中捕获错误并支持按具体问题生成新版本。

还有一类问题是代码能执行但体验不合理，例如操作窗口太短、动画尚未看清就被销毁。解决方式是记录实际操作反馈，调整规则或结束时机，而不是继续放宽语法检查。

5 内网模型慢的原因需要用返回数据确认

Qwen3.8-Flash-Next 最初部分请求把 4096 个输出 Token 全部用于思考，正文为空。模型名称大小写还使原先的配置分支漏掉了关闭思考参数。修正识别并增加可配置输出额度后，记录仍显示发送关闭参数却实际产生大量思考。

进一步对内网服务做两次极小文本核验：顶层 enable_thinking: false 仍产生 42 个思考 Token；使用 chat_template_kwargs.enable_thinking: false 后为 0。随后对 S08 两个原有点、保留两张图片和 16384 输出额度做一次玩法验证，约 20.2 秒返回两条推荐，思考 Token 为 0。

与此同时，原来的每批五点请求多次约 180 秒收到网关 504。程序客户端设置的 300 秒并不能消除上游限制。我将批次改为可配置，并为该内网配置每批两点，不删除图片，不自动重试失败批次。

最后还修复了接口返回 prompt_tokens_details: null 时的用量汇总错误。现在失败批次与已完成批次分别记录，缺失用量保留为未知，不再因为统计异常覆盖真实失败原因。这次两点验证确认了参数和小批次能正常工作，不能外推为全部视频的速度或质量提升。

八 我如何测试和判断效果

1 真实调用比较内容和稳定性

我用同一视频重复运行不同提示词，查看是否找到类似行为、位置是否接近、理由是否对应画面，而不只比较措辞。对动作前后、普通空镜、多人物及小目标等情况分别观察。

测试阶段已有结果对结论的约束
Day1 模型体验阶段报告记录四模型、两模式、四素材共 32 次调用完成接口与描述对照，不等于已获得人工准确率
Day2 v12六次双模型运行均有候选，共 23 个两模型输入与音频条件不同，不作为公平排名或正确率
Day2 v13S05、S06、S01、S04 各两轮，报告记录共 16 次调用、18 个候选增加可检查的中间过程，仍有主体和动作错误
Day3 v20十组流程，28 次请求；第三步八次中六次结构通过，形成 28 条可读推荐两组失败原文仍有玩法草稿；可读覆盖不等于玩法正确率
内网收尾验证S08 两点一次推荐，约 20.2 秒，2/2 有推荐，思考 Token 为 0只确认这次参数与调用成功，内容仍有身份推断

各阶段统计来自相应运行和报告，实验条件并不全部相同，不相加成为统一成功率。历史报告中的版本描述也可能与后续同名文件不同，实际调用的提示词全文和参数才是复现实验的依据。

2 本地测试保证工程行为

后端使用 Python unittest，模型响应通过模拟替代；前端使用 Node 测试覆盖页面状态和调用协议。检查内容包括时间映射、空结果、非法引用、输出截断、部分失败、请求构造、单点生成、版本过期、回收恢复及视频触发。

浏览器夹具用于验证弹窗、大屏、布局、暂停、启动和续播。夹具游戏能证明宿主流程，不计入真实模型游戏的成功样例。最近一次内网配置与批次修复完成了 21 项相关后端测试及前端检查；这是该次改动的回归范围，不代表本次整理文档时又执行了当前全部测试。

本地复现命令为 python -m unittest discover -s demo/tests -v，页面脚本检查入口为 node demo/tests/ui_smoke.js。真实调用另外记录，避免工程测试意外计费。

3 实际试玩检查操作和反馈

项目已有 S05 蓄力、拖拽，以及“女生准备起跑”连点修复等真实产物和运行回调。起跑样例根据“操作窗口太短”的问题修复，说明调试不只处理语法，也要处理玩家来不来得及操作。

我把四种结果分开理解：格式检查通过、语法检查通过、运行正常、体验符合设计。checked 只表示完成规定检查；success 回调可能表示游戏判定成功，并不等于人工确认玩法合理。反过来，正常规则触发的失败也不能当成程序崩溃。

九 为了让流程好用而完善的功能

页面从一页堆放全部内容，收敛为视频分析、交互点管理、玩法推荐与选择、游戏生成与管理、视频交互编排五个工作区。玩法描述、生成输入和版本详情采用弹窗，技术原文默认折叠，等待时间可见，减少页面过长和上下寻找的问题。

项目数据按用途分开：原始分析保存事实和模型输出，项目草稿保存用户编辑，游戏库保存各点版本，试玩记录单独归档。采用引用、输入哈希和视频 SHA-256 用来检查关联，避免换视频、改时间或改方案后误用旧代码。

游戏文件按模型、素材、玩点组织，文件名保留素材、类型、日期和生成阶段；JS、CSS、设计独立导出。删除游戏版本或交互点时进入项目回收站，连同关联产物和试玩文件处理，支持恢复而不覆盖后来的选择。

配置也从依赖 .env 改为页面设置，支持模型、服务地址、密钥和工具路径，提供导入导出及用量查看。设置按工作流快照使用，运行中的任务不被中途修改配置影响。配置文件中的密钥仍是本地明文，应与可公开的项目代码和成果分开管理。

这些改动的目的，是让用户可以不断回看、试错、保存和继续工作；界面与文件管理调整应尽量复用已有生成结果，避免为了改善展示再次计费生成。

十 项目收获与后续复用

这次项目让我形成了几个比较明确的认识。

首先，AI 工作流需要可检查的中间结果。事实描述、参与设想、具体玩法和实现代码有不同的正确性标准。拆分之后，可以只修改出问题的一步，不必每次从头调用。

其次，提示词优化需要服务任务本身。约束过多会压缩机会，完全放开又会放大联想；更合适的做法是让各阶段承担清楚的职责，把时间、引用等可验证条件交给程序，把创意留给模型，把体验选择留给用户。

第三，模型调用的成功只是工程链路的一部分。参数被接受，不等于关闭思考生效；图片被发送，不等于画面被正确理解；代码能解析，不等于玩家能顺利完成。这些问题都需要对应的证据和测试方法。

最后，失败记录、版本关联和用户反馈是继续优化的基础。保留原文可以区分输出错误与本地处理错误；保留修复前后版本可以解释做了什么改动；保留运行反馈可以判断是否值得采用，而不只是展示一次看似成功的结果。

后续接入影游平台时，可以复用阶段化接口、画面 ID 与时间映射、玩法目录、单点生成协议、版本追溯、试玩记录和视频宿主逻辑。进一步工作应优先补齐跨题材人工验证、关键动作局部时序输入，以及多用户任务管理、权限和运行资源隔离。

本阶段交付的是一套能够围绕具体视频持续创作和调试的原型。它已经把任务书要求的主要环节连起来，也保留了哪些判断需要人工、哪些问题尚未完全解决的边界，为后续接入平台和继续改进提供了可复用的基础。
