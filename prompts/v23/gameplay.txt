# 任务：根据画面与事件推荐适合玩家参与的玩法
你负责视频分析器的第三步。输入包含已发现的交互机会、对应画面、事件文字，以及预设小游戏类型。重点回答：这里可以怎么玩？玩家做什么？为什么这种玩法与当前情境有关？

画面与事件提供情境，玩法可以设想新的下一步，不必照实拍视频的后续发展。区分已经发生的事实与新设计的行为：不要把设想写成视频事实。以当前画面确认人物、物体及其关系；旧事件和机会文字可能不准确，位置调整后尤其如此。先明确玩家参与的是谁的行为，避免让持球人把球传给自己等主体混乱。

timing、hold_release、swipe、drag、tap_object、mash、choice 七种玩法地位平等，不设首选类型或固定排序。依据当前画面、参与目标与玩法适配程度推荐；choice 可以独立成为最合适的方案，也可以与其他玩法并列，不默认作为备选。机会文字中出现“决定”或“选择”不等于一定适合 choice，仍需说明不同选项的情境依据与取舍价值。

区分输入方式与玩法目标：点击按钮可以承载策略选择，拖向某个对象也可能包含对象之间的取舍。不要仅因为某个选择能用点击、拖拽或滑动实现，就排除choice；也不要把单一动作加一个确认按钮便称为决策玩法。

先确定玩家参与的行为，再检查适合的操作：
- timing：把握行动的启动、接收或执行时机，用一次适时按下来参与。
- hold_release：按住积累力度或程度，在合适时松开。已经取得物体、尚未完全抬手，也可以设计成蓄力释放，不必先写成几个动作的选择题。
- swipe：通过短滑表达移动、躲避、起跳或换向，重点是方向输入。
- drag：把一个对象移到另一位置，表达传递、对准、放置或拨开。
- tap_object：指出、选中或确认画面中具体可见的人、物、目标或路径。
- mash：用重复点击表达持续施力、冲刺或累计推进。
- choice：让玩家在有情境依据的不同方案、意图或回应之间作出取舍。fit 说明决策价值；有第二方案时，说明二者参与目标与体验的实际差异。

七种玩法均按行为与情境匹配，不为凑齐类型而推荐。每个点最多提供两个真正不同的玩法，按适配程度排序，不按类型排序；一个合适方案即可。两个方案只换文案或控件、参与目标与体验却相同，不算不同玩法。没有与当前情境相关的具体参与想法时可以不推荐。

用简明具体的文字说明：fit 场景与玩法的关系；player_goal 玩家目标；player_action 玩家如何参与；success、failure 操作完成或未完成的大致条件；feedback 玩家得到什么回应。这些是玩法设想，暂不要求精确时限、角度、坐标、按钮数组、命中比例或关卡参数。不生成 JavaScript 或其他代码。是否暂停、如何播放、是否接回原视频，留到选定玩法后的实现设计，不作为推荐门槛。可以描述游戏内反馈，但不要承诺已经实现，也不要拿未拍到的结果充当事实。



# 本批逐点覆盖
输入是全部已选交互点中的一批，本批最多五个点。仅处理本次提供的 point_id，不推测其他批次，不重新编号。
必须逐点回应：每个 point_id 要么在 recommendations 中返回一至两个合适方案，要么在 abstentions 中明确说明当前画面为什么没有合适玩法。不得遗漏，也不得把“没分析完”说成“不适合交互”。
允许不推荐，但理由应具体关联当前主体、对象、状态或参与目标；不能使用“略”“无”“没有提供”代替分析。不为满足覆盖要求强行设计玩法。
返回前核对 recommendations 和 abstentions 合起来已覆盖本批全部 ID；两者不能为同一点同时出现，不输出检查过程。七种玩法仍按场景适配选择，不设固定优先级。

# 输出字段与约束
只输出合法 JSON 对象，不用 Markdown，不输出推理过程。
- recommendations：必需数组，可以为空。每个对象包含 point_id、game_id、fit、player_goal、player_action、success、failure、feedback；这些字段均为非空字符串。title、difference 可选，提供时用非空字符串。
- point_id 必须原样复制输入中的交互点 ID；game_id 必须取自本次提供的目录，每点最多两条推荐。
- abstentions：本批存在未推荐点时必须提供的数组；提供时，每项必须是对象，包含输入中存在的 point_id 和非空字符串 reason。不得写成字符串数组。已推荐的点不得同时出现在 abstentions 中，同一点不重复说明原因。没有未推荐项时为空数组或省略。
- 不需要 choice_labels、direction、target_labels、parameters、坐标或代码。参与设想与已观察事实分开表达。
