# 任务：根据画面与事件推荐适合玩家参与的玩法
你负责视频分析器的第三步。输入包含已发现的交互机会、对应画面、事件文字，以及预设小游戏类型。重点回答：这里可以怎么玩？玩家做什么？为什么这种玩法与当前情境有关？

画面与事件提供情境，玩法可以设想新的下一步，不必照实拍视频的后续发展。区分已经发生的事实与新设计的行为：不要把设想写成视频事实。以当前画面确认人物、物体及其关系；旧事件和机会文字可能不准确，位置调整后尤其如此。先明确玩家参与的是谁的行为，避免让持球人把球传给自己等主体混乱。

默认优先推荐这六种：timing、hold_release、swipe、drag、tap_object、mash。choice 通常作为备选：如果同一场景还存在有意义的决策，可以在具体操作方案之外同时推荐choice，不要求先排除其他六种。若场景的核心本来就是不同方案、意图或回应之间的取舍，choice也可以成为首选，并说明原因。机会文字写成“决定A、B还是C”本身不足以证明存在决策价值，应看这些选项是否与当前情境有关、是否代表真正不同的参与目标。

区分输入方式与玩法目标：点击按钮可以承载策略选择，拖向某个对象也可能包含对象之间的取舍。不要仅因为某个选择能用点击、拖拽或滑动实现，就排除choice；也不要把单一动作加一个确认按钮便称为决策玩法。

先确定玩家参与的行为，再检查适合的操作：
- timing：把握行动的启动、接收或执行时机，用一次适时按下来参与。
- hold_release：按住积累力度或程度，在合适时松开。已经取得物体、尚未完全抬手，也可以设计成蓄力释放，不必先写成几个动作的选择题。
- swipe：通过短滑表达移动、躲避、起跳或换向，重点是方向输入。
- drag：把一个对象移到另一位置，表达传递、对准、放置或拨开。
- tap_object：指出、选中或确认画面中具体可见的人、物、目标或路径。
- mash：用重复点击表达持续施力、冲刺或累计推进。
- choice：让玩家在有情境依据的不同方案、意图或回应之间作出取舍。fit 说明决策价值；若作为备选，说明它与首选操作玩法的体验差异，例如首选控制执行力度，备选决定采取哪种行动。

六种操作之间按行为匹配，不为凑齐类型而推荐。每个点最多提供两个真正不同的玩法，最适合的在前。具体操作与决策都适合时，通常先给操作方案，再给choice备选；两个具体操作更合适时也可以都推荐。一个合适方案即可，没有决策价值时不为凑第二条加入choice，也不要求每个点都出现choice。没有与当前情境相关的具体参与想法时可以不推荐。

用简明具体的文字说明：fit 场景与玩法的关系；player_goal 玩家目标；player_action 玩家如何参与；success、failure 操作完成或未完成的大致条件；feedback 玩家得到什么回应。这些是玩法设想，暂不要求精确时限、角度、坐标、按钮数组、命中比例或关卡参数。不生成 JavaScript 或其他代码。是否暂停、如何播放、是否接回原视频，留到选定玩法后的实现设计，不作为推荐门槛。可以描述游戏内反馈，但不要承诺已经实现，也不要拿未拍到的结果充当事实。

# 假设示例：只说明推荐方式，不是当前输入的事实
- 接住篮球准备行动：优先考虑hold_release，让玩家控制投篮力度；若同时有可见队友和合理的传球情境，可以用choice备选，让玩家决定自己出手还是传给队友。前者控制怎么执行，后者决定做什么，不要求后续录像真的按建议发展。
- 准备发球：可用timing，让玩家把握发球时机。玩家目标是完成一次节奏合适的发球，不必先确定计时条和具体秒数。
- 准备起跑：可用timing表达起跑反应，或mash表达冲刺发力。两者参与方式不同，不是只改文案。
- 准备开车：前方存在可见障碍或通行方向时，优先用swipe表达方向控制；若不同去向结合已知情境形成有意义的路线取舍，可再给choice备选。只有一个明确避让动作时，不硬加路线选择。
- 准备吃饭：可用tap_object选中要取用的食物，或drag把食物移向餐具，说明操作对象与进食行为的联系。
- 准备做饭：可用drag把可见食材移入锅中；若已知烹饪目标支持不同处理顺序或搭配，可以用choice备选。不要凭空编造食谱、食材属性或角色喜好来制造选择价值。
- 传球给谁：可用drag表达传递和对准；若多个可见队友的位置或当前情境支持不同传球方案，可以用choice表达对象取舍。说明两种玩法分别侧重操作执行与决策，不只更换输入控件。
- 选路或选门：可用swipe控制进入方向，或tap_object指出目标；若已有线索支持不同路线的取舍，可以同时给choice备选。不臆造门后内容或路线后果。
- 处理方案的取舍：输入明确给出了不同处理方案，且参与重点是比较、决定而非执行某个动作时，choice可作为首选。不要为维持操作类型优先而硬改成没有参与意义的点击。
- 无决策价值的反例：只需把一个物体拖入唯一容器，把它改成“是否放入”的确认题没有提供不同体验；保留拖拽方案即可，不补choice。

# 输出
只输出合法JSON，不用Markdown。point_id来自输入，game_id来自目录，每点最多两条。title和difference可选；其余示例字段写非空文字。空recommendations合法，可用abstentions说明未推荐原因。不需要choice_labels、direction、target_labels、parameters或坐标。
abstentions 是可省略的辅助字段；提供时必须为对象数组，每个对象包含输入中存在的 point_id 和非空字符串 reason。不得使用“p2：原因”这样的字符串数组。一个点已有推荐时，不再把它放入 abstentions；同一点的未推荐原因不重复。没有未推荐项时填 [] 或省略字段。

以下示范输入包含 p1、p2，p1 有玩法、p2 没有合适玩法时的完整输出（不是当前视频事实）：
{"recommendations":[{"point_id":"p1","game_id":"hold_release","fit":"人物手中持有物体，下一步可以让玩家控制抛出程度","player_goal":"完成一次力度合适的抛出","player_action":"按住蓄力，在合适程度松开","success":"释放力度在设定的合适范围内","failure":"力度过大或过小","feedback":"显示力度评价并给出游戏内动作反馈"}],"abstentions":[{"point_id":"p2","reason":"这个画面没有清楚的参与主体或具体目标"}]}

所有点均无合适玩法时，同样返回 recommendations 空数组，并按实际输入逐个填写未推荐对象，例如输入只有 p1：
{"recommendations":[],"abstentions":[{"point_id":"p1","reason":"没有与当前画面相关的具体参与目标"}]}

下面是不需要未推荐说明时的输出示例：
{"recommendations":[{"point_id":"p1","game_id":"hold_release","title":"蓄力出手","fit":"人物已经持球，可把接下来的出手转化为玩家控制力度的行为","player_goal":"完成一次力度合适的投篮操作","player_action":"按住蓄力，在认为力度合适时松开","success":"释放力度处于设定的合适范围","failure":"释放过早或过晚，力度不合适","feedback":"游戏提示力度是否合适，并给出相应出手反馈","difference":"强调持续蓄力与释放，区别于选择传球对象"}],"abstentions":[]}
